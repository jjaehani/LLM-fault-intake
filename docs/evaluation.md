# 추출 성능 기록

`scripts/evaluate.py`로 [가상 증상 데이터](../data/symptoms.csv) 19문장을 채점한 기록이다.
채점 기준은 접수 여부, 되물을 항목, 장비 이름, 작동 상태가 정답과 같은지다.

## 1차: 기본 프롬프트

- 모델: gemini-3.5-flash-lite
- 결과: 통과 10, 실패 9

| 원인 | 문장 |
|---|---|
| 장비 이름이 정답과 다름 (컨베이어 벨트, 압축기, 선반) | S-003, S-006, S-008 |
| 증상만 보고 작동 상태를 짐작함 | S-011 |
| "이상해요", "고장났어요"를 증상으로 받음 | S-014, S-015 |
| "멈췄다"를 작동 상태로만 보고 증상을 비움 | S-001 |
| 정보 없이 급하다고만 한 메시지를 접수가 아니라고 봄 | S-016 |
| 장비가 두 개인 메시지 | S-017 |

## 2단계: 산업용 전자 장비와 증상 분류

장비를 HMI, 인버터, 서보드라이브, PLC, 산업용 PC, 파워서플라이 6종으로 바꾸고 증상 분류 코드 추출을 추가했다. 데이터는 조정용 `dev.csv` 20문장과 시험용 `holdout.csv` 12문장으로 나눴다. 프롬프트는 `dev.csv` 결과만 보고 고친다.

### 2단계 1차

- 결과(dev): 통과 16, 실패 4
- D-002, D-010, D-015: "화면이 안 나온다", "전압이 안 나온다", "모터가 안 돈다"를 보고 작동 상태를 채웠다. 1단계의 기계 장비는 장비가 멈추면 곧 작업이 멈췄지만, 전자 장비는 설비에 들어가는 부품이라 부품 고장과 라인 정지가 다르다. 작동 상태를 라인과 작업 기준으로 다시 정의했다.
- D-018: 장비 두 개. 1단계와 마찬가지로 두 번째 장비(서보드라이브)를 버렸다.
- 증상 코드는 장비가 두 개인 D-018을 빼고 모두 맞았다.

### 2단계 2차

- 바꾼 것: 작동 상태를 부품이 아니라 라인과 작업 기준으로 정의
- 결과(dev): 통과 18, 실패 2
- D-002, D-010, D-015가 통과했다.
- D-016("장비 에러 났어요")은 1차에서 통과했는데 2차에서 실패했다. 이 문장과 관련된 규칙은 바꾸지 않았으므로, 같은 입력에도 모델 답이 실행마다 달라서 생긴 실패다. "에러 났다"를 모호한 표현 목록에 넣었다.
- 실행마다 결과가 흔들리므로, 한 번 돌린 점수만으로 규칙의 효과를 판단하지 않는다.

## 실행 중 만난 문제

| 문제 | 원인 | 조치 |
|---|---|---|
| `429 You have no credits remaining` | OpenAI 계정에 크레딧 없음 | 무료 등급이 있는 Gemini API로 변경. 코드는 OpenAI 호환 주소로 연결해 그대로 사용 |
| `404` | `gemini-2.5-flash`는 모델 목록에 있지만 이 키로 호출되지 않음 | 문장 하나로 모델 여러 개를 시험해 `gemini-3.5-flash-lite` 선택 |
| `503`으로 채점 중단 | 서버 일시 과부하. 호출 한 번이 실패하면 스크립트 전체가 멈춤 | 10초, 30초 쉬고 재시도. 그래도 실패하면 그 문장만 오류로 세고 계속 진행 |

503 중단은 요구사항 FIT-NF4(LLM 호출이 실패해도 접수가 사라지지 않아야 한다)를 챗봇에 구현할 때도 같은 방식으로 처리해야 한다.

## 2차: 장비 목록과 추측 금지 규칙 추가

- 바꾼 것: 장비 이름 목록, 모호한 증상과 작동 상태를 짐작하지 않는 규칙
- 결과: 통과 15, 실패 4

| 문장 | 결과 |
|---|---|
| S-001, S-006, S-008, S-014, S-015, S-016 | 1차 실패에서 통과로 바뀜 |
| S-010 | 새로 실패. "작업 못 하고 있어요"를 직접 말한 작동 상태로 보지 못함. 규칙이 너무 엄격해짐 |
| S-003, S-011 | 증상을 보고 작동 상태를 채움 |
| S-017 | 장비 두 개. 알려진 한계 |

S-003, S-010, S-011은 프롬프트에 작동 상태의 정의가 없어서 생긴 실패다. 화면 설계에서 챗봇이 묻는 질문("지금 작업이 멈춘 상태인가요?")에 맞춰 정의를 넣기로 했다.

## 3차: 작동 상태 정의 추가

- 바꾼 것: 작동 상태를 "지금 그 장비로 작업을 할 수 있는지"로 정의하고, 직접 말한 표현과 짐작하면 안 되는 표현의 예를 넣음
- 결과: 통과 18, 실패 1

S-003, S-010, S-011이 통과했다. 남은 실패는 S-017(장비 두 개)이다.

S-017은 2차에서 "프레스, 컨베이어"로 두 장비를 모두 적었지만, 3차에서는 컨베이어만 남기고 프레스를 버렸다. 실패 개수는 같아도 접수 하나가 사라진 결과라 더 위험하다. 한 메시지를 여러 접수로 나누는 기능을 만들기 전까지는, 장비가 두 개 이상이면 담당자에게 넘기는 방식을 검토한다.

## 주의: 이 점수는 실제보다 높다

2차와 3차 규칙의 예시는 이 19문장의 실패를 보고 만들었다. 같은 문장으로 다시 잰 점수라 처음 보는 문장에서의 성능은 알 수 없다. 규칙을 만들 때 보지 않은 문장으로 따로 잰다.
